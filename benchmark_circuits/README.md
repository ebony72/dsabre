# Benchmark circuits used in the dSABRE paper

Every circuit cited by a table or figure in `paper/dsabre.tex` and
`paper/appendices.tex`, collected into one place so a reader can re-run the
routers without first tracking down `~/Documents/telesabre/circuits/` (a
directory shared — and occasionally mutated — by several sibling projects on
the authors' machines, not part of this repository) or the two `code/`
subdirectories the synthetic families live in.

All 42 files below were verified by exact CX-gate count against the numbers
printed in the paper before being copied here (script: see "How this folder
was built"). Nothing here has been regenerated or altered from the source
copy — these are the literal files the results were computed from.

## Suite-by-suite detail

### `qasm_25/`, `qasm_36/`, `qasm_64/` — MQT Bench application circuits

Downloaded from **MQT Bench v1.1.0** (2024-03), basis `{rz, sx, x, cx}`,
Qiskit `optimization_level=3`, no coupling map
(`nativegates_ibm_qiskit_opt3_{n}`). Every file whose first line reads
`// Benchmark was created by MQT Bench on 2024-03-...` is an unmodified
v1.1.0 download. `qaoa_64` and `multiplier_64` are the two exceptions: MQT
Bench v1.1.0 does not offer these two circuit families at exactly 64 qubits,
so they were generated separately with the *installed* v2.2.2 algorithm-level
constructors (`code/gen_new_64q_circuits.py`) — QAOA p=2 dense random
max-cut, and a 16-bit `MultiplierGate`, both then transpiled with the same
basis/opt-level/seed as the rest of the suite. Their header comments read
`// Generated for the extended 64q suite with MQT Bench v2.2...` accordingly.

**`qnn_25`/`qnn_64` are the deep, fully-entangling form**
(`ZZFeatureMap(reps=2) ∘ RealAmplitudes(reps=1)`), not the shallow product-state
form the *installed* MQT Bench v2.2.2 would generate by default for the same
benchmark name. This matters: the two forms differ by two orders of magnitude
in CX count (8126 vs 63 at 64 qubits) and the shallow form cannot discriminate
between routers. The file was briefly overwritten with the shallow form by an
unrelated project sharing the source directory, caught, and restored — which
is why the CX table at the end of this file is the check that matters. **If you regenerate any MQT Bench
circuit from scratch rather than using the files here, verify the CX count
against the table below first** — a mismatch means a different construction,
not a rounding difference.

**Excluded on purpose**: the shared source directory `qasm_64/` also contains
`vqe_su2_64` and `wstate_64` — 64-qubit circuits under 36q-suite names,
generated by a different project sharing that directory. They are not part of
dSABRE's published 64-qubit suite (`benchmark.py`'s `CANONICAL_CIRCUITS`
whitelist excludes them) and are not copied here.

### `qasm_100/`, `qasm_200/`, `qasm_360/` — scalability rows

`qft` and `qpeexact` are copied at these three sizes — the two families the
revised `tab:main` scales while holding core occupancy roughly constant (6, 12
and 20 cores of 25 physical qubits). `qpeexact` at 100/200/360q was added on
2026-08-19: the submitted paper scaled QFT alone, and the three files were
verified by exact CX count (3579 / 7579 / 13979) against the revised table
before being copied. The source directories also contain MQT Bench downloads
for other families (ghz, graphstate, qnn, random, vqe_su2, wstate at 100/200q;
bv, dj, vqe_su2, wstate at 360q) — none of these are cited by any table in the
current paper at these qubit counts (confirmed by exhaustive grep of
`dsabre.tex` and `appendices.tex` for every `100q`/`200q`/`360q` occurrence),
so they are left out to avoid implying a reproducibility claim this repository
doesn't make.

360q's TeleSABRE cell in `tab:main` is `---` (marked `$^\ast$`, non-convergent)
— this is not a bug in the circuit or the architecture; see
`../CHANGES_FROM_SUBMITTED.md` §7/§7a for the full investigation, including a
direct re-confirmation that TeleSABRE fails the same way on the corrected
architecture (10/10 internal attempts exhaust their safety valve without a
successful pass).

### `regcz/` — degree-swept mechanism ablation (Appendix, `app:regcz_sweep`)

Synthetic: a random *d*-regular interaction graph on 64 logical qubits,
layers of single-qubit rotations each followed by a CZ across every graph
edge (construction: `code/gen_regular_cz.py`, same shape pytket-dqc ships as
`RegularGraphHypergraphCircuit` for its own benchmarks). `d ∈ {2,3,4,6,8}`,
three random interaction graphs per degree (`_s0`/`_s1`/`_s2`), 15 circuits.
Layer count is tuned per degree to hold CX near 2000 (within 4% for every
file here) so that only interaction locality varies, not gate volume.

### `regcz_scaling/` — circulant scalability family (Appendix, `app:regcz_suite`)

Same construction, but the interaction graph is a **circulant** (qubit *i*
joined to *i*±1, *i*±2 around a ring — degree 4, bounded range) rather than a
random regular graph, so the inter-core traffic fraction stays flat as *n*
grows instead of climbing with it (a random regular graph's locality decays
with *n*, which would make the series measure the graph rather than the
machine — see `app:regcz_suite` for the argument in full). 17 layers, giving
3400 / 6800 / 12240 CX at 100/200/360 qubits — deliberately close to the
banded QFTs' 3420/7220/13300 so the two scalability families are comparable
in gate volume. Generated by `code/gen_regcz_scaling.py`.

**Excluded on purpose**: `code/circuits_regcz_scaling/` also contains
`regcz_d3_n{100,200,360}.qasm` (degree 3, 23 layers, an earlier
parameterization of the same script). These are not cited anywhere in
`dsabre.tex` or `appendices.tex` — the only circulant numbers the paper
reports (`app:regcz_suite`: "$-39.2\%$ at 100q ($692$ against $421$ EPR) and
$-45.7\%$ at 200q ($1551$ against $842$)") match the degree-4/17-layer family
by CX count, not the degree-3 one — so the degree-3 files are left out to
keep this folder's contents exactly reproducible against the paper text.

## How to route these yourself

See `../REPRODUCE.md` and `../code/benchmark.py` / `../code/bench_large.py` for
the full driver setup. In short:

```bash
cd ../code
python3 -c "
from qiskit import QuantumCircuit
from qiskit.converters import circuit_to_dag
from router import General_dSABRE_Router
from dsabre_ext import dSABRE_BurstExt
from architecture import build_b_grid_architecture
from config import HardwareConfig
from layout import locality_aware_layout, run_passes
import random

qc = QuantumCircuit.from_qasm_file('../benchmark_circuits/qasm_25/qft_nativegates_ibm_qiskit_opt3_25.qasm')
dag = circuit_to_dag(qc)
arch = build_b_grid_architecture(r=2, s=2, m=4)
hw = HardwareConfig()
router = dSABRE_BurstExt(arch, hw)
layout = locality_aware_layout(dag, arch, rng=random.Random(0))
metrics = run_passes(router, dag, layout, 3)
print(metrics)
"
```

This minimal example runs a single seed and layout, so its `eprs` will not
match `tab:main` exactly (which reports the best of 3 `SabreLayout` seeds,
each run forward → backward → forward and scored on the better of passes 1
and 3 — see `../code/benchmark.py`'s `bench_suite` for the full protocol).
Use `benchmark.py`/`bench_large.py` directly for a number comparable to the
paper.

For TeleSABRE, point the binary at the matching device JSON in
`~/Documents/telesabre/devices/` (see `../REPRODUCE.md`, "TeleSABRE baseline") —
those device files are architecture descriptions, not benchmark data, and are
not duplicated here.

## How this folder was built

Every file was selected by (1) grepping both `.tex` files for every
occurrence of the relevant qubit count to find every table that could
possibly cite it, then (2) counting `cx` gates in the candidate source file
and requiring an exact (or, for the degree-swept ablation, ≤4%) match against
the number printed in that table. No file is included on the strength of a
filename or directory match alone.
